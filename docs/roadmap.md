# 版本路线图

## 0.9.14 验收范围

1. 总览首屏以「已使用」为主数字，「剩余预算」为次数字。
2. 总预算与使用比例以小结展示，不再使用大号字体。
3. 超预算和未设置预算的状态显示正确。
4. 本机 `npm run check` 与 GitHub Actions 全部通过。

## 0.9.9 已交付范围

1. 备忘专栏删除与撤销接口恢复正常；非空专栏二次确认后连同备忘一并软删除。
2. 外置 PostgreSQL 改为单条 `DATABASE_URL`。
3. 移除 SMTP 配置与邮件服务依赖。

## 0.9.8 已交付范围

1. 不传 `DATABASE_URL`、只挂载 `/app/data` 的容器可以正常启动，健康接口返回 `0.9.8`。
2. PostgreSQL 18 / 17 与外部数据库配置仍用空的 `DATABASE_URL` 清除镜像默认值，实际连接 `PG*` 指定的数据库。
3. 镜像部署命令包含基础文件 `compose.yaml`，启动后存在数据卷和数据库地址。

## 0.9.7 已交付范围

默认只需复制 `.env.example` 为 `.env`、设置 `APP_ORIGIN`，再执行 `docker compose up -d --build --wait`；外置 PostgreSQL、目录挂载和预构建镜像均为显式可选配置。

## 0.9.6 已交付范围

1. Web 与小程序的 JSON 文件可以互相导入，保留专栏、描述、重点与确认状态。
2. 完整导出、空专栏、中文、重复导入与 1000 条分批均有协议和自动测试覆盖。
3. Web 验证事务、权限和 PostgreSQL 18 / 17；小程序云端事务、失败重试及真机文件操作按各自环境验收。

文件互通只覆盖备忘内容，不等同于完整微信账号与装修账本迁移。

## 0.9.15 的迁移原则

从微信导入必须先建立经过核实的旧身份到新账号映射，不能靠昵称或用户输入 openid 认领。先只读导出和预览，再做批次导入；保留源 ID、软删除和历史时间，逐项核对预算、已付、待付和材料计划。

这与已有的 Web 内置/外置数据库迁移是两个工作：前者还涉及旧集合字段与身份转换，后者复制现有关系模型。

## 附件存储的后续选择

0.9.16 可将文件放到服务器目录，也可接 S3/OSS/COS 等对象存储，数据库只保存私有对象引用与元数据。数据库外置不自动等于附件外置，二者应独立配置和迁移。

## 1.0 之后

- 按客厅、厨房、卫生间等空间查看预算、材料与成本。
- 家庭可复用的装修流程和采购模板。
- 预算变更历史与剩余费用预测，明确区分预测和已记成本。
- 按真实需求决定是否接入 AI 分类和票据识别，不让它抢占数据可靠性与基础体验的优先级。

每版控制在一个主题内。如果某项能力依赖前版的数据结构，应先落 schema 与迁移，再做界面和集成。正式 schema 迁移、备份诊断等继续作为后续运维改进，不属于本次部署修补范围。
