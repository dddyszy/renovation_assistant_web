# 数据库结构演进

适用版本：0.9.17。当前 schema 来源为 `server/schema.sql`，PGlite 与外置 PostgreSQL 共用相同业务表。

## 当前启动行为

`server/db.ts` 在每次启动时读取 `schema.sql`，按分号拆分并依次执行语句。主要使用：

- `CREATE TABLE IF NOT EXISTS`
- `CREATE INDEX IF NOT EXISTS`
- 表内约束与索引定义

因此新增表、新增索引可以幂等执行；已有表不会被重复创建。**但修改已有 `CREATE TABLE` 语句不会升级旧表**：不会新增字段、修改类型、补充约束或回填数据。

当前没有 `schema_migrations` 表、迁移执行历史或自动回滚框架。

## 存储切换与结构升级不同

| 工作                                    | 工具                                     |
| --------------------------------------- | ---------------------------------------- |
| PGlite 与 PostgreSQL 之间复制同版本数据 | [存储迁移](storage-migration.md)         |
| 旧版本数据库升级到新结构                | 需要正式版本化迁移，目前没有自动执行框架 |
| 外置 PostgreSQL 主版本升级              | 数据库侧逻辑备份/恢复，不由应用自动处理  |

切换数据库地址、替换镜像或重新执行建表语句都不能代替结构升级。

## 新变更的检查顺序

1. 判断是新增幂等对象，还是修改已有对象。
2. 评估旧版本应用是否会继续读写同一数据库。
3. 设计扩展与收缩步骤，避免一次发布同时要求新旧结构都不可用。
4. 添加迁移、回滚或兼容方案，以及从旧结构开始的测试。
5. 停止写入并备份，在隔离环境完成恢复和金额/关联核对。
6. 记录发布版本、执行结果和回退边界。

## 后续迁移机制建议

建议优先补齐最小能力，不急于引入大型框架：

```text
schema_migrations(
  version TEXT PRIMARY KEY,
  applied_at TIMESTAMPTZ NOT NULL DEFAULT now()
)
migrations/
  001_initial.sql
  002_xxx.sql
```

- 启动或独立发布任务中按版本顺序执行；每个迁移记录只执行一次。
- 多语句迁移使用事务，并选择支持事务的 DDL。
- 外置 PostgreSQL 使用 advisory lock 防止多实例并发执行；PGlite 继续保持单进程。
- 失败立即停止启动，不跳过未完成的迁移。
- 生产发布保留备份和回滚步骤，不自动删除字段或数据。

## 测试要求

- 从上一版结构创建数据，再执行新迁移。
- 验证旧数据、外键、软删除、金额和版本字段。
- 重复执行迁移保持幂等，失败不会留下半批结构。
- PGlite 与外置 PostgreSQL 分别验证；17/18 使用同一套结构规则。
- 数据库回滚前处理新版本产生的数据，不能直接用旧备份覆盖新增记录。

正式迁移框架落地前，文档和发布记录必须明确结构变更，不得把“启动成功”当作旧库已正确升级。
